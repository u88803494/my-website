## 可能會需要

### 思考方向

我覺得可能要往兩種方向來思考，一種是如何透過前端實現，當然前端的資料其實不安全。第二種是透過改後端資料庫跟 API 來實現，這樣相對比較安全，也是比較正規的寫法。

### 登入部分：

管理使用者的資料庫，紀錄第三方登入的 user 資料，然後此欄位的 userID 可以給文章的資料庫紀錄對應關係。

這部份實作上也有可能可以困難一些，像是要如何組織多重第三方登入，不過我想只是簡短說明應該不用這麼複雜，但我覺得這個可以放在未來可以改進的方向這邊。而這邊好像就是 noSQL 的優勢，可以任意添加 key & value

### 文章 API

文章 API 需要砍掉重練，因為要對應使用者資料庫的 userID，外加設定權限等級。

新增一個管理文章的界面，也因應前面，所以可以每個人可以在自己的管理文章界面看到自己的文章了，而最高權限管理者則是都可以看到。

又或是只有需要審核的人才看得到，或是根本不需要管理界面。就是登入的時候，最高管理人可以看到文章審核了沒而已即可，這部份都有待思考。

### 畫面相關

畫面的部分，因為是需要非最高權限使用者發文之後，還沒通過審核前，就無法給別人看到，所以最高權限登入的情況下是文章都會顯示，但是還沒通過審核的就會有個按鈕，跟文章的顏色會比較淡這樣。

## 如何介紹？

因為這次需要面對的是除了 RD 之外，還有業務跟設計師，所以不能單純講技術的，必須要生活化一些。

先說明目前系統的狀況，然後要做的目標，接著說明以現況來說，會遇到的困難，根據這個困難，可能要汰換掉哪些部分。接著說明汰換或新增的部分，會用到哪些部分，像是資料庫的方式，而資料庫這邊因為是說要我用熟悉的部分來說明，所以就會以 mySQL 為主，但也要準備一下被問 noSQL 的時候該怎麼回應。

資料庫的說明，會員系統的資料庫，文章系統的資料庫，兩者如何建立關聯。

後端的程式碼，這邊直接假設，可以直接呈現出 JSON 格式的資料就好，主要是因為時間限制只有 5~10 分鐘，太細節的部分不適合講太多。但是也是要規劃一下 API 如何串接使用的。這邊當然就需要一張簡報。

有了 API 之後，就可以設置開始寫前端程式，因為有了登入功能，所以登入時候，就可以根據取得的資料判斷權限等級，因為決定哪些資料要不要 render。
