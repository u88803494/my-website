## 提要：

### 公司現況

稍微說一下公司同事的組成以及公司的現況，我入職的公司是間新創公司

我入職的時候成員目前是 CTO + 全端工程師 x 2＋設計師 + 業務，但一個月後有一名全端離職，這讓我感覺這個產業真的跟我之前的工作不一樣了。

我的上層主管是 CTO，但其實他同時也是老闆，只是新創的關係，不會特別說是老闆。

而我進來公司就先提供三個月的訓練期，所以這三個月我就都沒有開發壓力，還可以多問問題，所以整體來說我是進到不錯的一間公司，甚至我的壓力來源都是我自己給自己的，哈哈。

### 我的技能組合

前端：React + Redux + JS + CSS + HTML

後端：PHP + MySQL + AWS EC2

前端只是比較熟一點，後端的話大概就是有碰過而已。

### 公司的技能組合

前端：React + Redux + SCSS

後端：Express.js + MongoDB + GitLab CI/CD + Azure + TypeScript

後端比重很重，因為是個五年內的新創，又是做 B2B，所以前端比較沒這麼重視。

好處是除了前端部分之外，後端也有，甚至 CI/CD 也有，部署也整個自動化（含自動化測試），可以學的東西很多。

## 入職第一個月：後端大魔王

先解說一下為什麼叫做大魔王好了。根據前述，我的後端技能原則上在這間公司，是無法通用的，而我後端部份，也只是有接觸到皮毛而已，所以對我來說肯定就像是個大魔王一樣，需要花很多時間去理解跟挑戰。

接下來就進入正題了。老實說，過這麼久真的有點忘記當初到底做了些什麼XD

只好去翻翻 GitLab，只記得自己利用 express.js + mocha 做了個請假系統。

在這裡，直接開了一個新專案。要求我建立一個請假系統的後端。

用以學習整個開發流程，因為是用 GitLab，跟之前學的 GitHub 有點不太一樣，但嚴格上來說差不會太多。

在這邊 GitLab 是先寫好 issue 之後，直接在 GitLab 上面透過 issue 開好 Merge Requset 之後，再從遠端 pull 下來，也因此，所以就直接用第幾個 issue 的編號來命名即可，我自己是覺得這個流程還不錯。

所以先開了個 issue 叫做 overview，但實際上只是寫個總覽，而在這邊就是先設計想一下整個請假系統會需要些什麼。

而這個 issue 並沒有開下去做，所以我剛剛才發現那個 issue 至今沒有 close。:D

所以接下來寫的都是我有實作的 issue。

### 第一個 issue:

> **Establish Node.js with Express for Development**

> **Goal**
> `GET localhost:3000/hello` server should respond `World` with status code `200 GET localhost:3000/db` server should respond with the content from `db.stats()` and code `200`

> **Further requirements**
> es6 transpile
> eslint
> unit test with `mocha` and `chai`

而初次建立專案之後，就是很簡單的建立專案，但難的部分很快就來了，因為我後端沒用過 node.js，而這邊要直接用 Express.js，所以說實在的梯度真的很高。而且 node.js 原生也不支援 `import`，所以我就必須要另外安裝 babel 才行。

除了要用 express 串 MongoDb 外，同時間也要用 eslint，還加上 BDD 的 unit test，感覺負荷一下就超過之前學習程式了XD

為此我就開始去到處找資料，也因此理解到了很多名詞，黑箱白箱測試、TDD/BDD 真正地差異、斷言庫、command line 上的環境變數等。

環境變數算是讓我比較驚訝的一部分，因為原來我可以透過設定環境變數很方便的啟動我的伺服器。

而公司對於順序的要求也讓我滿訝異，像是 pacgage.json 要按照官方文件的順序排序，雖然我當時沒想到要問為什麼要這樣做的原因，不過我猜這樣做是方便之後去找資料對比。也因此我分清楚 `devDependencies` 跟 `dependencies` 的差異。

除此之外 script 的部分也是，我終於比較懂得那些 `npm run xxxxx` 到底要怎樣設定，因為除此之外還有 `pre-` 開頭的設定，像是 `prestart` 就是可以指定要在 `npm run start` 之前先執行的腳本。

code 就不用說了，引入除了要照字母順序之外，還要分為從 package 引入跟從其他檔案引入，還有分常數跟通用 function，整個都規模化起來的感覺。

而另外一個挑戰是因為這是間很重視英文的公司，所以在進入這間公司後，所有的 issue、Merge Request 都要用英文寫，註解也是，當然 commit 也是。這樣算是提早給我英文的挑戰吧，因為我之後也想練好英文。

好，然後還有一個挑戰是人的挑戰，因為我們每天都要 standard meeting，所以我就要開始練習怎麼說自己要做什麼。

### 第二個 issue:

因為比較複雜 Medium 很難以呈現，所以我改為直接寫出要做什麼的標題。

> **Create CRUD APIs for user. (with authority)**

這裏就開始挑戰使用 async 跟 await，然後是用一個叫做 `MongoMemoryServer` 在本機啟用虛擬的 MongoDB 來做測試，然後為每一個 APIs 盡量寫出可能會遇到的各種問題，所以在這裡就真正地搞懂 TDD 以及 BDD 的差異。

在這裡大量練習斷言庫的使用，以及 done 在什麼時機使用。當然最重要的是要怎麼樣 CRUD MongoDB 內的資料。

然後在這邊我還玩了一個 issue 內沒有要求的功能，我開始研究如何讓 code 在我儲存之後自動 complie，然後 restart，為此我先找了兩個 package 來使用，第一個忘了名字 no 開頭的，第二個我用了 `babel-watch` 。

然而這些其實都不是真正地挑戰。真正地挑戰是要開始學習看官方文件，直接從官方文件找出蛛絲馬跡，然後開始直接實作要的功能。所以看了好幾個官方文件：[Express.js](https://expressjs.com/)、[MongoDB 的 package](http://mongodb.github.io/node-mongodb-native/3.6/api/)、[Mocha](https://mochajs.org/)、[Chai.js](https://www.chaijs.com/api/assert/) 等，其餘還有數個小的 package，就不一一說明了。這一切都是為了要達成，整個小專案的目的。

而我覺得比較困難的當然就是 Express.js 以及 MongoDB 的部份了，畢竟是這個專案最主要的內容，而 Express 的部份，雖說我之前課程上有資源，但最後卻發現，很多新的 API 以及在更新之後，本來需要額外安裝的 package 的功能也都被內建進去了。

所以在這個階段就是開始學習如何從官方文件正確的找到需要的資訊。

### 第三個 issue：

> **feat: Create leave system APIs**

可以看到這次的 issue 標題也長得不一樣，多了個 「**feat:**」。

這是因為通過前面比較熟悉那些工具以及公司的模式之後，就開始進入更嚴格的要求了。

在這裡開始變成寫 issue 會要求要盡量詳細，然後還需要分幾個細項來寫，如下：

> Summary
> Behaviors
> Possible Implementations

這邊整體就是一個請假系統，要有使用者的 APIs，然後第三個就是做請假的 APIs 了。困難點在於，我必須要跟 users APIs，做結合，也就是說，在使用者針對 leave(請假) APIs 發送 Request 的時候，必須要先驗證使用者的身份，去分可以誰可以執行哪些 API，誰不行。

然後也開始要求我使用資料格式，像時間要做成符合 ISO 8601 的格式。ID 則是因應 MongoDB 的關係，也改用 uuid，對我來說這一切都是沒聽過得名詞，只能查，然後找可以用的 package，都花了我非常多的時間。

也因為變得嚴格，所以**開始要求我變數以及 function 的命名**，要盡量精簡易懂，像是這邊是利用 Express 在寫 Router，所以本來命名 `usersRouter` 就是不行的，要命名為 `users` 才可。

也因為這邊要做請假系統，所以要請假的話自然就是一堆狀況了，以下僅列出幾種：

1. 我不能針對已經請過的假期，再去做一次申請。
2. 不能一次請超過七天假。
3. 一次請假最少要一天。

當然還有非常多種情況了。

還有針對權限的問題：

1. 一般使用者只能看到他自己的假
2. 主管可以看到全部人
3. 只有主管可以審核假

等……。

> 題外話：也因為要做這個 issue，我去網路上找了很多資料，然後突然靈機一動，我突然想到之前面試一家好像是做員工系統的公司，一搜，原來光是請假系統，就有不少公司專門再做，而且規模還不小XD

接著繼續說下去，因為需要做很多的驗證以及檢查，我就展開了寫複雜邏輯的路…，但想當然爾，比較複雜的我是寫不出來的。還好的是之前公司也有很多人做過這個練習，所以就參考他們的即可。但我覺得還是要自己消化過，所以我就看過他們的理解之後，自己重新寫過。

在這裡自己寫，然後我才發現原來我也可以把 code 寫得很抽象，因為再做檢查中，可以要先解析資料，然後在驗證，然後另外一個驗證是依賴另一個驗證的資料。

但又不能寫到太詭異，所以我就做了像是下方的 code：

```
const result = (col, username, ask, id) => {
  ...
  ...
  ...
  ...(做了一堆事情)
  ...
```

```
  return (
    isOverlap(parseDates(ask), getUserLeaves(allUserDetail))
  );
}
```

簡單說我把 `parseDates(ask)` 以及 `getUserLeaves(allUserDetail)`的回傳值傳進去當成引數，然後 return 值是依賴另外一個函數的回傳值。這樣寫可以把每個 function 是做什麼的，清清楚楚的寫出來，所以我才這樣寫。

在這裡也練習很多，像是我不去依賴 for 迴圈，因為說真的現在寫 code 好像很少人在用迴圈了，大部分都是利用 array 的 method 去解，所以這裡也大量練習使用 array 的 method，讓我覺得對於 JS 是更加地熟悉。像我這邊就用到 `.some()` 跟 `.every()`，也算是收穫很多吧。

其他部份，就是像測試，必須要盡量把各種情況都測出來，寫著寫著，我開始先寫測試，才開始寫 API，這時候，我才發現原來之前別人寫說，先寫測試才寫 code 是真的會比較好寫，因為一邊寫就一邊直接測了，看結果，然後在修正 code。
