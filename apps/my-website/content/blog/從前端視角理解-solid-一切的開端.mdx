最近一次的面試，我被問到一個既熟悉又陌生的問題：「你了解 SOLID 原則嗎？在你的專案中是如何應用的？」

這個問題，讓我想起了幾年前的一段經歷。當時我正帶領一個全新的 React 專案，一位寫 Java 的 App 同事，總是在專案會議上把 SOLID 掛在嘴邊。在當時，我正全心專注於產品的快速交付與團隊的開發流程，雖然聽進去了，卻沒有機會去深究這個名詞背後的完整體系，但「SOLID」這個詞就此在我腦中留下一個索引。

直到這次面試，為了能清晰地回答問題，我開始系統性地回顧自己的開發習慣：我如何拆分複雜的元件、如何設計可複用的 Hooks、如何定義清晰的 Props 介面。面試結束後，我投入時間將這些實踐經驗與 SOLID 的理論定義進行對照，這才迎來了我的「啊哈時刻」（Aha moment）。

更讓我驚訝的是，我發現 **SOLID 原則的精神，不僅能很好的應用於函數式程式設計 (Functional Programming) 的概念上，甚至 React 自身的設計，尤其是在 Hooks 問世之後，其背後的核心思想都與 SOLID 不謀而合**。例如，將邏輯抽離至 Custom Hook，本身就是「單一職責」與「依賴反轉」的絕佳體現。

原來，這些原則的靈魂早已超越了 `class` 的語法，並深深地影響著現代前端的架構。也因此，我決定將這段學習歷程整理成文章，分享給所有可能跟我一樣，在實踐中摸索，卻需要一條理論線索來將所有知識串連起來的前端夥伴。

## 我們都曾踏入的「技術債」泥潭

在討論解方之前，讓我們先回到一個真實的場景。

你是否也曾參與過一個快速迭代的前端專案？專案初期，我們意氣風發，元件乾淨、邏輯清晰。但隨著時間推移，需求不斷變更、功能持續堆疊，情況開始失控：

- **一個失控的元件：** 一個 `UserProfile.tsx` 元件，從一開始的 50 行，膨脹到 500 行。它既要負責打 API、又要處理表單狀態、還要應對三種不同的使用者權限，最後再渲染出複雜的畫面。這個元件成了團隊裡沒人敢碰的「不定時炸彈」。
- **恐懼變更的文化：** 「牽一髮而動全身」成了日常。你想重構一小段邏輯，卻發現它與十幾個地方都有耦合。你盯著那段程式碼，心想：「算了，先複製貼上，能動就好…」技術債就這樣悄悄地累積。
- **寸步難行的測試：** 你想為某個核心功能寫單元測試，卻發現光是模擬（mock）它所依賴的十幾個 props 和服務，就比寫測試本身還累，最後只好無奈放棄。

這就是「高耦合、低內聚」的典型症狀，也是專案從靈活敏捷，走向開發地獄的警訊。

## SOLID：前端開發的「架構心法」

面對上述的困境，SOLID 原則為我們提供了一面「透鏡」，讓我們能看懂為何 React Hooks 如此強大，也讓我們能更有意識地去打造穩健的系統。

它並非一套生硬的規則，而是一系列經過驗證的思考框架，一套幫助我們打造出優雅程式碼的設計心法：

- **單一職責原則 (S)** 讓我們理解，為何將邏輯抽離至 Custom Hook 是一種優雅的實踐。
- **開放/封閉原則 (O)** 讓我們在添加一個新的「主題配色」或「會員等級」時，可以透過擴充，而非修改核心的判斷邏輯。
- **里氏替換原則 (L)** 確保我們擴充的元件（例如 `<PrimaryButton>`）不會違背基礎元件（`<BaseButton>`）的行為承諾，讓系統行為可預測。
- **介面隔離原則 (I)** 提醒我們不要設計一個有 20 個 props 的「上帝元件」，而是讓每個元件只向外索取它真正需要的東西。
- **依賴反轉原則 (D)** 引導我們依賴抽象（例如一個 `IAuthService` 介面），而不是具體實作（例如 `FirebaseService`），讓元件變得可獨立測試、可輕易抽換。

遵循這些原則，能讓我們更有意識地寫出符合 React 精神、且經得起時間考驗的程式碼。

## 結論：

深入理解 SOLID 原則的過程，讓我對許多早已熟悉的程式設計概念，如柯里化（Currying）、高階函式（Higher-Order Functions）有了全新的體悟。我意識到，無論是 SOLID 還是函數式程式設計，它們的誕生，都是為了解決一個共通的目標：**如何讓我們的程式碼擁有更高的可控性與更好的可讀性**。

學海無涯，我認為理解這些更底層的設計哲學，能讓我們在規劃程式結構時，擁有更清晰的藍圖與更堅實的信心。這份信心，也將讓我們在與 AI 協作的時代，能更好地引領 AI 寫出真正優雅且強固的程式碼。
